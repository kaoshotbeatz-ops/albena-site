**Do not implement Phase 2 unchanged.** The Hub authorization boundary is a sound direction, but bootstrap can enroll an attacker’s key, execution lacks ordering guarantees, and the WebAuthn RP ID conflicts with existing credentials.

References below are to the [design](controls/threat-models/portal-connector-control.md). These are design findings, not demonstrated runtime exploits; no files were edited.

1. **Critical — Bootstrap comparison does not authenticate the customer’s key.** (§2.2, lines 64–73) A compromised portal can supply an attacker key, produce its assertion, and display the matching fingerprint on both screens. The user faithfully comparing six words still enrolls the attacker. A QR containing a nonce alone does not fix this. **Fix:** establish enrollment through an independently trusted native app or local authenticated ceremony that binds the actual credential, Hub identity, role and fresh Hub nonce. Disable portal-mediated bootstrap and recovery until that binding is specified.

2. **High — WebAuthn RP ID is incompatible with current registration.** (§2.3, line 91) The design requires `SHA-256("account.albena.ai")`, while [wrangler.jsonc:23](portal/worker/wrangler.jsonc:23) configures `RP_ID: "albena.ai"` and registration uses that value. Existing passkeys will fail the proposed Hub verifier. **Fix:** explicitly choose the RP ID, pin it with each trusted credential, and retain exact origin checking. Narrowing the RP requires new credential enrollment, not just changing the hash. Use a WebAuthn verifier with explicit COSE algorithm handling. [WebAuthn specification](https://www.w3.org/TR/webauthn-3/#sctn-verifying-assertion)

3. **High — “Privilege-reducing” commands can still cause unauthorized destruction.** (§2.3, lines 98–100) A substituted assertion can disconnect a security connector or remove protective functionality without Hub confirmation. This contradicts “A1 … cannot cause a change.” **Fix:** independently approve every configuration mutation initially. Later exempt only narrowly defined, reversible operations whose availability impact is explicitly accepted.

4. **High — Trust-root administration lacks safe authority rules.** (§2.2, lines 71–74) “Any trusted passkey” may remove another, potentially allowing a household member to remove the owner. “Quorum” actually means one key plus a PIN. Role assignment, owner transfer and recovery invalidation are unspecified. **Fix:** define an owner-only authorization matrix; bind key, role and identity into enrollment approval; require local confirmation for administrative removal; increment a trust epoch and invalidate pending commands after recovery or trust changes.

5. **High — Replay protection is not an execution state machine.** (§2.3, lines 82–96; §4) Nonce checking does not specify atomic reservation, concurrent execution, crash recovery or post-approval checks. A delayed `read→write` can execute after a newer downgrade; an already-prompted command can survive signer revocation. **Fix:** persist command states atomically, use resource revisions/preconditions and trust epochs, and recheck expiry, signer, role, halt and current state immediately before execution. Define idempotent recovery for interrupted external operations and fail closed on clock rollback.

6. **High — Independent approval is asserted, not secured.** (§2.3–2.4) `destructive=True` blocks one shortcut but does not establish that voice, automation, another API or an unrelated pending approval cannot satisfy the request. App authentication and PIN protections are absent. **Fix:** bind approval to one immutable command hash and expiry through an authenticated, independently paired UI. Rate-limit PIN attempts, protect PIN storage, reject generic “approve latest,” and exclude voice approval from MVP.

7. **High — Portal lifecycle operations and Hub authority are not reconciled.** (§3; CONTRACT account/security APIs) Portal passkey deletion and household removal do not revoke Hub trust. Deleting a Hub row does not revoke its OAuth tokens. The reviewed [heartbeat handler](portal/worker/src/hubs/index.ts:281) still returns authoritative-looking settings; whether deployed Hubs ignore them was not verified. **Fix:** separate portal record removal from authenticated Hub revocation; show pending/offline status; cancel queued work and revoke provider grants where supported. Verify every Hub consumer ignores unsigned configuration, including update-channel changes.

8. **High — HPKE is reasonable cryptography, but the protocol is incomplete.** (§3) Mode, wire format, `info`, key identification and unambiguous AAD encoding are unspecified. Concatenated variable-length identifiers are ambiguous. Rotation does not provide forward secrecy for ciphertext encrypted to a retained recipient key. Portal secret entry also directly contradicts the unconditional “never holds a usable secret” claim. **Fix:** remove portal secret entry for MVP. If restored, specify a vetted HPKE suite and fresh encapsulation per message, structured context binding, bounded parsing and key deletion policy. State the custody limitation explicitly. [RFC 9180](https://www.rfc-editor.org/rfc/rfc9180.html)

9. **High — OAuth lacks end-to-end account and grant binding.** (§3, line 119) Displaying a code does not establish which provider account, tenant or actual scopes were authorized. The portal-only comparison fallback supplies no independent evidence. **Fix:** initiate authorization locally, pin provider endpoints/client configuration, and bind the transaction to the command. Before enabling the connector, display the returned account and granted scopes on the trusted Hub UI. Reject excess scopes and expire/cancel abandoned grants. [Device authorization security considerations](https://www.rfc-editor.org/rfc/rfc8628.html#section-5)

10. **High — MCP allowlists do not enforce tool semantics or prevent exfiltration.** (§5) Hiding tools from `tools/list` is insufficient unless the dispatcher also enforces authorization. A malicious “read” tool may mutate remotely; unchanged tool names can gain malicious behavior. Prompt injection can leak one connector’s data through another tool’s arguments without a write call. **Fix:** enforce policy at invocation, pin schemas and implementations where possible, isolate connector data contexts, and authorize cross-connector disclosure and outbound destinations. Treat remote read/write labels as untrusted claims.

11. **High — MCP network and process isolation are underspecified.** (§5) DNS pinning is ineffective if the actual client resolves again or bypasses the proxy. LAN exceptions may expose sensitive local services. An unprivileged user and seccomp do not alone define containment; two alternative Mac sandbox mechanisms are not a tested policy. **Fix:** force all network paths through enforcement, validate actual destination IP/port and TLS identity, tightly scope LAN exceptions, and deny direct sockets. Specify filesystem/IPC access, capabilities, resource limits, subprocess policy and immutable executable provenance. [MCP security guidance](https://modelcontextprotocol.io/docs/draft/tutorials/security/security_best_practices)

12. **High — “Compromised Hub damage stays on that Hub” is false.** (§1, A7) Stolen provider tokens may expose cloud accounts shared by several Hubs; a compromised Hub can attack reachable LAN systems. Local trust files, backups and reset paths are also outside the stated boundaries. **Fix:** document provider-account and LAN blast radius, use distinct least-privilege grants where available, isolate networks, protect trust storage from connector processes, and define provider-side incident revocation.

13. **Medium — A signed kill switch can be replayed or withheld.** (§4, line 137) A compromised distribution path can serve an older valid manifest or suppress the halt. Signature verification establishes authenticity, not freshness. **Fix:** use monotonic policy versions, validity windows, persisted highest-seen versions and an explicit stale-policy behavior. Keep disablement latched until independently authorized recovery. Do not claim reliable emergency delivery through the compromised portal.

14. **Medium — Audit integrity and compliance are overstated.** (§4, lines 145–146; §6) A local hash chain can be rewritten; anchoring to the compromised portal does not guarantee independent detection. A passkey signature over substituted content does not prove informed transaction consent. WebCrypto or an OpenSSL provider name does not establish FIPS validation for the deployed configuration. **Fix:** use independently retained signed checkpoints, document the unanchored interval, record transaction-bound approval evidence, and label mappings as proposed controls awaiting validation. Name exact module certificates, versions and approved operating modes before claiming FIPS coverage. [NIST CMVP](https://csrc.nist.gov/projects/cryptographic-module-validation-program)

15. **MVP cut — Ship local connector management with portal status only.** Defer remote mutations, portal HPKE entry, arbitrary MCP/stdio, household administration, voice approval and push approval. Support a small audited connector catalog, Hub-local secret entry, least-privilege grants and local disconnect/revocation. This removes most of the new authorization protocol. If remote commands are essential, start with one reversible operation, independent local confirmation, authenticated bootstrap and the durable execution checks above.

No production behavior or test-suite results are claimed. The work-log helper failed under the read-only sandbox; its existing log was read directly, and no completion entry was written.
